# フェーズ1 レビュー結果 (Opus 4.6)

## 総合評価

フェーズ1の4項目（モノレポ初期化 / Nuxtセットアップ / Supabaseスキーマ / 共通型定義）は**骨格としては揃っている**が、いくつかの項目で「最低限の初期化だけで完了とした」印象が強い。フェーズ2にそのまま進むと手戻りが発生する箇所がある。

---

## 1. モノレポ構成 (Bun Workspaces) -- 評価: B

**良い点:**
- ルート [package.json](package.json) の `workspaces: ["apps/*", "packages/*"]` が正しく設定されている
- `apps/web`, `apps/cli` (.gitkeep), `packages/shared` の各ディレクトリが存在し、OVERVIEW.md の構成図と一致
- `bun.lock` が生成されており、依存関係の解決が完了している
- [apps/web/package.json](apps/web/package.json) で `"@nusk/shared": "workspace:*"` が正しく参照されている

**課題:**
- **ルートに `tsconfig.json` がない** -- モノレポ全体の TypeScript パス解決やコンパイラオプションの共通基盤が未整備。各ワークスペースから `@nusk/shared` を型安全にインポートするための `references` や `paths` 設定がない
- **`packages/shared/tsconfig.json` がない** -- shared パッケージ自体の型チェックが `tsc` で実行できない
- **ESLint / Prettier 等のリンター設定が一切ない** -- コード品質の基盤がフェーズ1で整備されていない
- **`.npmrc` や `.bunfig.toml` がない** -- Bun Workspaces のホイスティング挙動の制御が未定義

---

## 2. Nuxt.js + Nitro セットアップ -- 評価: C

**良い点:**
- Nuxt 3.21.2 がインストールされ、`nuxt dev` で起動可能な状態
- `app.vue` が存在し、最低限のアプリケーションシェルがある

**課題 (重大):**
- **`nuxt.config.ts` がほぼ空** -- `compatibilityDate` と `devtools` のみ。以下が全て未設定:

```typescript
// 現状 (apps/web/nuxt.config.ts)
export default defineNuxtConfig({
  compatibilityDate: '2025-07-15',
  devtools: { enabled: true }
})
```

- **`@nuxtjs/supabase` モジュールが未インストール** -- フェーズ2で認証を実装する際に必要。フェーズ1の段階で Supabase 接続の疎通確認ができていない
- **`runtimeConfig` が未設定** -- `.env` に `SUPABASE_URL` / `SUPABASE_ANON_KEY` / `SUPABASE_SERVICE_ROLE_KEY` が定義されているが、Nuxt の `runtimeConfig` に反映されていない
- **`app.vue` がデフォルトのまま** (`NuxtWelcome`) -- テンプレートの雛形すら未構築
- **`server/` ディレクトリ内に API ルートやミドルウェアが0件** -- Nitro の動作確認がされていない
- **`devDependencies` が未定義** -- `@types/node` 等の開発依存が未記載

---

## 3. Supabase スキーマ定義 -- 評価: B+

**良い点:**
- マイグレーションファイルが2つ存在し、`docs/SCHEMA.md` のSQLと完全に一致
- テーブル構造（`lists`, `statuses`, `tasks`, `personal_access_tokens`, `push_subscriptions`）が要件定義通り
- 適切なインデックスが定義されている
- RLS が全テーブルで有効化されている

**課題 (重大):**
- **RLS ポリシーが一切定義されていない** -- RLS を有効化したが、ポリシーが0件のため、**全てのクエリがデフォルトで拒否される**。これはフェーズ2の認証実装時に確実にブロッカーになる。最低限 `auth.uid() = user_id` のような基本ポリシーが必要
- **`updated_at` の自動更新トリガーがない** -- `lists`, `statuses`, `tasks` 等の `updated_at` カラムは `DEFAULT NOW()` のみで、UPDATE 時に自動更新されない。`moddatetime` 拡張か、カスタムトリガーが必要
- **`(user_id, is_inbox)` のユニーク制約がない** -- 1ユーザーが複数の Inbox を作成できてしまう設計。少なくとも `is_inbox = TRUE` の場合に1レコードに限定する部分ユニーク制約 (`WHERE is_inbox = TRUE`) が必要
- **`seed.sql` が存在しない** -- `config.toml` で参照されているが未作成。開発時の初期データ投入ができない
- **`status_id` への ON DELETE 挙動が未定義** -- `tasks.status_id REFERENCES statuses(id)` に `ON DELETE` がないため、ステータス削除時に整合性エラーが発生する

---

## 4. 共通型定義 (packages/shared) -- 評価: B

**良い点:**
- Supabase CLI (`supabase gen types`) で生成された正確な型定義ファイル [packages/shared/types/database.ts](packages/shared/types/database.ts)
- [packages/shared/index.ts](packages/shared/index.ts) でドメインモデル型（`Task`, `List`, `Status` 等）をエイリアスとしてエクスポートしており、消費側の DX が良い
- `Row` / `Insert` / `Update` の3パターンが全テーブルで定義されている

**課題:**
- **`Tables` / `Enums` ヘルパー型の名前衝突** -- `index.ts` で `export * from './types/database'` した後に同名の `Tables` と `Enums` を再定義しており、`database.ts` 側の汎用版がシャドーイングされる。意図的であれば問題ないが、`database.ts` の `TablesInsert` / `TablesUpdate` は使えるのに `Tables` だけ挙動が異なるのは混乱の元
- **`Relationships` 配列が不完全** -- `lists`, `personal_access_tokens`, `push_subscriptions` の `Relationships` が空配列 (`[]`)。`user_id` -> `auth.users.id` の外部キー関係が型に反映されていない（Supabase gen types の制限の可能性あり）
- **API リクエスト/レスポンス用の型が未定義** -- `docs/API_ENDPOINT.md` に基づくリクエスト/レスポンス型（例: `CreateTaskRequest`, `TaskListResponse`）がない。フェーズ2で API を実装する際にここが必要になる
- **`tsconfig.json` がない** (前述の通り)
